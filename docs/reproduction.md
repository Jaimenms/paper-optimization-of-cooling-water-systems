## Discrepancies that are not errors of the paper

1. **Local optima of a non-convex MINLP (Case 2, Case 1B).** The problem is non-convex (Merkel
   equation, P-NTU effectiveness, Hazen-Williams, bilinear velocity bounds) and both the SBB +
   CONOPT runs of the paper and the branch-and-bound used here return local optima. In the two
   cases where the designs differ, the reimplementation found slightly *better* objective
   values (0.01 % and 0.02 % lower) with the same pump and a different set of small pipe
   substitutions; the Case 2 solution of the GAMS listing (189 783.46 USD/y) is also 22.6 USD/y
   above the one found here. The ranking of the cases (Figs. 9–10) and every conclusion of the
   paper are unchanged. SCIP (global solver, `SolverSettings(name="scip")`) finds the same
   solutions as primal heuristics, but the dual bound of this MINLP is too weak to prove global
   optimality in useful time.
2. **Pipes 5 and 6 are interchangeable (Case 1C).** Pipes 5 (supply, node 5 → 6) and 6 (return,
   node 7 → 8) have the same length (100 m), the same existing diameter (6 in) and carry the same
   flow (E-104 + E-105). Enlarging either one to 8 in has exactly the same cost and the same
   hydraulic effect on circuits 4 and 5, so "pump 4 + pipe 5 → 8 in" (paper) and "pump 4 + pipe
   6 → 8 in" (this work) are the same optimum (flows, valves and penalties of Table 11 identical).
3. **Budget sweep point B = 2437.5 USD/y.** The GAMS listing `part4_case01_redo` keeps one point
   of the sweep (objective 87 139.39 USD/y, pipes 1 → 14, 9 → 5, 13 → 2.5, 14 → 5 in). The cached
   sweep gives 87 134.90 USD/y at the same budget with pipes 1 → 14, 6 → 8, 13 → 2.5, 14 → 6 in:
   again a slightly better local optimum. The curves of Figs. 7–8 are visually identical.
4. **Purely hydraulic solution (Table 12).** The objective of Section 3.7 (sum of squared
   deviations between cooler flow rates and the desired ones) is almost flat with respect to the
   E-105 flow rate (its target is 3.16 kg/s, the deviation ~10 kg²/s² against ~370 for E-102).
   The reimplementation reaches a lower objective (523.3 vs 524.0 kg²/s²) by also downsizing the
   E-105 branch (pipes 13, 14 and 18) within the Case 1A budget, which starves E-105 (0.02 instead
   of 0.073 kg/s). The economic evaluation of that cooler is extremely sensitive at such flows,
   hence 341.8 vs 320.0 kUSD/y; the conclusion of the paper (the purely hydraulic approach
   yields a far worse economic result, 452.7 vs 86.9 kUSD/y for Case 1A here) is reinforced.
5. **Figures without printed values (Figs. 4, 7, 8, Video 1).** They are reproduced from the
   sweeps (`results/penalty_sweep`, `results/budget_sweep`) and compared visually; the paper
   prints no numbers for them except the ~3 kUSD/y threshold of the pump purchase.
6. **Bonmin instability (tool, not paper).** Bonmin (B-BB through the CasADi wheels) reproduces
   Case 1 in ~30 s but aborts (`Uncaught error in Bonmin`, segmentation fault) in Case 2 even with
   conservative settings and in an isolated process. The default solver is therefore the
   NLP-based branch-and-bound `coolingnet.optimization.nlpbb` (IPOPT nodes, SOS1 branching,
   valve multi-start, final local search); Bonmin, IPOPT and SCIP remain available.
7. **Spurious root of the regularized Merkel equation.** The first Bonmin run of Case 2 returned
   a "zero penalty" design (53.4 kUSD/y) with the tower basin at the wet-bulb temperature and a
   negative enthalpy driving force at the top of the packing: a non-physical root created by the
   `+1 J/kg` regularization of the GAMS code. The model adds `Hsat_m − H_m ≥ 100 J/kg` at every
   quadrature point (`cooling_tower.min_enthalpy_driving_force_J_kg`); the published solutions
   satisfy it by a wide margin (> 40 kJ/kg), so no published number changes (erratum E2).

## Notes on the original GAMS code (`legacy/gams`)

The GAMS project (`artigo.gpr`, `coolingnetwork_applied_v21_part*.gms`, SBB + CONOPT, GAMS
24.x) is the authors' own code and is kept read-only; the listings (`.lst`) and logs are the
primary evidence for the published numbers. `scripts/parse_gams_lst.py` extracts the `Display`
blocks into `data/reference/d4_*.json` (see `data/reference/README.md` for the map listing →
paper item); `make eval` compares them with the cache (`gams_listings.csv`).

* `part0` holds the data and the model; `part1`/`part2` the simulations of the existing network
  (`part2_initial`, `part2_actual` → Table 8); `part2_actual_simulation` the desired flow rates
  of Table 12; `part3` the unlimited-budget cases (Table 10); `part3_quad_dif` / `part3_forced`
  purely hydraulic variants not shown in the paper; `part4_case01*` the budget sweep (Figs. 7–8,
  Video 1); the R post-processing that drew the figures was not part of the material copied.
* **Merkel quadrature abscissae**: `alfa_torre = 0.1, 0.4, 0.6, 0.7`, whereas the text says
  `0.9` (erratum E1). The packaged case keeps 0.7; notebook 01 shows the effect of 0.9.
* **Regularization** of the Merkel integrand, `1/(Hsat − H + 1)` (1 J/kg), not mentioned in the
  paper (erratum E2); kept as `cooling_tower.merkel_regularization_J_kg`.
* **Hazen-Williams**: exponent 1.85 on `c` (text and code), 1.852 on `q` (erratum E3); kept.
* **Big-M bounds** `q_min = 1e-5 m³/s`, `q_max = 100 m³/s` (Eqs. 17–18); the Python model uses the
  zero-head flow rate of the strongest pump as `q_max` (tighter, mathematically equivalent).
* **Penalties**: the code uses the binary formulation of Eqs. (49)–(54); the Python model uses the
  equivalent epigraph form `che ≥ pen (T_out − T_spe)`, `che ≥ 0` by default (exact when the
  penalty is minimized, better conditioned) and keeps the binary one as an option
  (`penalty_formulation="binary"`, needed for the flow-deviation objective of Section 3.7).
* **Tolerances**: `optcr = optca = 1e-3`; the same defaults are used by `SolverSettings`.
* The water viscosity of Table 7 appears in the data block but is not used by any equation
  (erratum E5).
